# Release workflow

## Branch flow

The repository includes a gix configuration for main, develop, feature, bugfix, hotfix and release branches.

~~~sh
gix doctor
gix feature start bilingual-template
gix feature finish
~~~

Use gix for version calculation and branch flow rather than maintaining custom git-flow shell scripts.

## Changelog

Use Conventional Commits such as feat:, fix:, docs:, refactor: and perf:. Generate release notes with:

~~~sh
px changelog
px changelog --version v1.2.0 --dry-run
~~~

Non-conventional subjects are skipped instead of being guessed.

## Version, tag and push

gix owns semantic version bumping:

~~~sh
gix version bump patch --dry-run
gix version bump minor
~~~

After reviewing and committing the changelog, create an annotated or signed tag:

~~~sh
px tag v1.2.0 --sign
~~~

The tag command refuses a dirty working tree. Push the current branch and, only when requested, tags:

~~~sh
px push
px push --tags
~~~

Build commands never commit, tag, push or create releases implicitly.

## Build and publish release assets with Pipeline

The GitHub release workflow is a thin caller of `m-mdy-m/pipeline/.github/workflows/release.yml@main`. Pipeline owns release preparation, tag validation, changelog selection, build matrix execution, asset normalization, checksum generation and GitHub Release publication. The Workspace workflow supplies project commands and the artifact glob only.

Push a SemVer tag to create a release. Tags with prerelease identifiers (for example `v0.3.0-alpha.1`, `v0.3.0-beta.1` or `v0.3.0-rc.1`) become GitHub prereleases automatically; stable tags become regular releases. Use the workflow-dispatch dry-run to exercise packaging without publishing.

The build produces:

- Python wheel and source distribution, checked with `twine check`.
- `papyrxis-workspace-release.zip`, a deterministic bundle containing both distributions, `PACKAGE-MANIFEST.json` and `SHA256SUMS`.
- Pipeline-generated release metadata, manifest and top-level checksums, plus keyless Sigstore signatures and GitHub artifact provenance attestations.

The bundle is verified before it is attached. Verify a downloaded bundle with:

~~~sh
python scripts/package_release.py --verify papyrxis-workspace-release.zip
~~~

Install from a downloaded wheel with `python -m pip install ./papyrxis_workspace-<version>-py3-none-any.whl`. The ZIP is a convenience bundle; it is not a substitute for installing the wheel through pip.

## Docker distribution

The version-tag workflow builds and smoke-tests a multi-platform image for `linux/amd64` and `linux/arm64`, then publishes to GHCR. It additionally publishes to Docker Hub when the repository has `DOCKERHUB_USERNAME` and `DOCKERHUB_TOKEN` Actions secrets configured. Docker Hub credentials are never committed or passed to PR workflows.

~~~sh
docker pull ghcr.io/papyrxis/workspace:<version>
docker run --rm ghcr.io/papyrxis/workspace:<version> --help
~~~

The image contains the Python CLI, LaTeX toolchain and Pandoc, runs as the unprivileged `px` user, and exposes the current directory as the recommended project mount point. The container workflow smoke-tests `px --help` and the multi-document example before pushing.

## Installable GitHub Package (GHCR OCI)

A second Pipeline reusable workflow publishes the verified Python distribution bundle as an OCI package at `ghcr.io/papyrxis/papyrxis-workspace`. This is distinct from the runnable Docker image at `ghcr.io/papyrxis/workspace`. The OCI package contains the self-verifying release ZIP and has a digest-addressed publication receipt generated by Pipeline.

Download the package by its immutable digest using ORAS (replace the tag with the release version or use the digest recorded by the publishing workflow):

~~~sh
oras pull ghcr.io/papyrxis/papyrxis-workspace:<version>-linux-amd64
python scripts/package_release.py --verify papyrxis-workspace-release.zip
~~~

GitHub Packages visibility and access are controlled by the GHCR package settings. The publishing workflow requires `packages: write`; consumers need read access to the package.
